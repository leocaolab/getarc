# 四路品味检查

一个人同时审安全和品位会顾此失彼：查安全的人想的是「这里还要加什么检查」，查品位的人想的是「这里能删掉什么」。所以分成四路，各自只想一件事，最后再合起来。Google 的代码审查也是这么分的：正确性由一位审查者负责，语言的可读性由另一位有 readability 资格的人负责。

## 步骤

1. **定范围，读规矩。**确定要审的文件或 diff。先读项目自己的规范：`CLAUDE.md`、编码规范和 `docs/` 里的设计文档。通用的写法标准在本插件的 `coding-convention` skill 和对应语言的 `shift-left-*` skill；规则原文在 `${CLAUDE_PLUGIN_ROOT}/rubrics/`。
2. **四路并行。**在同一条消息里派四个子 agent，每个只拿下面对应那一路的说明、审查范围和项目规范的路径。说明原样转交，不要转述。每一路交回一张表：发现、`file:line`、证据（引用代码原文）、它自己是怎么核实的。
3. **主会话核实。**每一条发现都自己打开代码核对。凡是涉及成本或调用方式的说法，要看调用方，或者实际数一次。核实不了的删掉，并写明为什么删。每条留下的发现都写清两件事：**在什么条件下会发生**（具体的输入、配置或时序），以及**多常见**（常见、少见、几乎不会）。只写后果、不写条件，读的人会把每一条都当成迫在眉睫。
4. **裁决冲突。**按下面的冲突规则处理。
5. **交结果。**一张表，再加一段综合结论，见文末格式。审完不改代码，改不改由人决定。

## 四路的说明

### 第一路：正确性

你只关心代码对不对。

- 非法状态能不能在类型上表达出来？能的话，指出该怎么改类型。
- 每个 `Option` / `Result` 对应的情况在现实里会不会发生？不会发生的，该改类型；会发生的，失败有没有带着真实原因交给能做决定的那一层？
- 边界条件两侧有没有测试，也就是刚好在线和刚好过线的输入？代码写坏时，测试真的会红吗？
- 外部输入参与的算术会不会溢出？
- 同一个不变量是不是在好几处各维护一份，彼此可能不一致？
- 输入空间大的纯函数，尤其是解析外部输入的（路由、请求头、路径、配置），有没有 proptest、fuzz 或 Kani 覆盖？没有的，指出该补哪一种。

### 第二路：安全

你假设所有输入都是恶意的，所有依赖都会超时。

- 外部输入（字节、请求头、路径、连接的快慢和断开）能不能让代码 panic？
- 内存有没有上限？有没有放大效应：一个请求刷爆日志、触发无界分配、引发 fork 风暴、长期占住资源？
- 并发：有没有数据竞争？有没有拿着锁去等 IO？`tokio::spawn` 或子线程里的 panic 会不会让任务悄无声息地消失？
- 你倾向于建议「再加一个检查」。每提一条，都写清楚这个检查要挡住的具体输入是什么。

### 第三路：设计

你只看结构，不看措辞。

- **纯粹性：**判断逻辑里有没有混进 IO（文件、网络、时钟、线程、打印）？有就要拆：判断写成纯函数，IO 留在外层。
- **透传：**有没有哪一层只是把参数原样转给下一层，自己什么判断都没加？
- **trait：**每个 trait 是不是有两个真实实现，或者测试必须靠它换掉副作用？只有一个实现的 trait 是多余的。
- **决定当数据：**判断能不能返回一个描述「要做什么」的枚举，交给外层执行，而不是自己去调 IO？
- **接口宽度：**用 grep 数一下每个 `pub` 项在模块或 crate 外面有几个调用方。没有调用方的不该公开。
- **信息泄漏：**同一份知识（一种格式、一个顺序、一条规则）是不是出现在两个模块里？
- **按执行顺序切分：**模块是不是按「先做什么、后做什么」切开，而不是按「各自掌握什么知识」切开？
- **类型归属：**类型是不是放在产出它、维护它生命周期的那个模块里？
- **过度设计：**有没有为将来也许会用到的需求留的扩展点？
- **外部依赖的名字和布局：**这个改动有没有改掉别人依赖的东西——公开 API（比如 Python 用户在调的类和参数）、配置项名字、指标名（看板和告警在用）、环境变量、跨进程共享的内存布局或线上格式？改了的话，有没有迁移方法和说明？

### 第四路：品位

你只关心读起来是否诚实、平直、省力。你倾向于删代码。

- **删行测试：**删掉这一行，行为变不变？不变的，就是多余的包装、凑类型用的拷贝、多余的 `forget` / `clone`。
- **特殊情况：**同一个边界条件是不是在好几个函数里各补一次？能不能换一种数据表示，让它变成普通情况？（Linus 讲链表删除的例子：用指向指针的指针，删除头节点就不再需要单独写 `if`。）
- **一个事实存一份：**能算出来的值是不是又单独存了一份？同一个排序是不是在两处各做了一遍？
- **线性：**函数能不能从上到下一条线读完？只为了「函数要短」切出来的三行小函数，该合回去。但为了把判断从 IO 里拆出来写的纯函数，不在此列。
- **名字：**哪个名字难起，哪个东西一句话说不清，就标出来。这通常说明结构有问题。
- **注释：**按项目规范审：读代码能懂就不写；每条注释都是一句完整的话；只写为什么、调用方看不见的坑和类型表达不出来的不变量。
- **物理成本：**请求路径上有没有多余的分配、拷贝、加锁和系统调用？提这类问题之前，先看调用方实际怎么用这个值。

## 冲突规则

- **事实和数据优先于偏好。**声称「这样更快」「这样省一次分配」的，要有调用方的证据或实测的数字，否则不收。
- **先找一个能同时满足各方的结构，再考虑取舍。**比如安全那一路要加检查、品位那一路要删分支时，先问设计那一路：能不能改类型，让这个状态根本表达不出来？或者让判断返回一个决定，由外层统一处理？
- **排序按概率乘以后果，不按后果单独排。**「后果是卡死」但要配一个 2900 亿年的超时才会触发，排在「后果是多打一行日志」但每个请求都会发生的后面。
- **真冲突时按这个顺序让步：**安全，然后正确，然后设计，最后品位。
- **品位不能把纯判断合回 IO 里。**线性可读不能以牺牲可测试性为代价。
- **每一条要改的发现都写清改成什么。**只说「这里不好」、不给改法的，不收。
- **不在项目规范里的纯风格问题，标 `Nit:`。**它不挡合并。

## 例子

- **被核实推翻的：**有人建议把 `panic_message` 改成返回 `&str`，理由是能省掉分配。主会话去看了调用方，发现几个调用方都把结果存进 `String` 字段，改了之后，分配只是挪到了调用方。这一条删掉。
- **两路一致、被收下的：**一个读 CPU 拓扑的模块为了证明「至少有一个核」，把第一个元素单独传了五层，其中一个函数甚至把一个永远是 0 的常量当成返回值传出去。品位那一路认为这是到处补特殊情况；设计那一路认为同一个不变量在五个函数里各维护了一次。结论：「非空」只在一处建立。

- **被概率降级的：**审一个线程运行时模块时有三条后果都很重的发现。复核触发条件后：「线程失败时先拆运行时、后公布失败」要同时遇到致命的 accept 错误和卡住的 handler，少见但后果是服务器无声地半死，值得修；「stop watcher 不取消 token」要 stdout 是已关闭的管道，少见，修法只有一行，顺手修；「超时相加溢出」要把超时配到约 9.2e18 秒，几乎不会，排到最后。

## 输出格式

```
| # | 路 | 发现 | file:line | 证据 | 核实 | 触发条件 | 多常见 | 后果 | 级别 | 改法 |
```

- 「核实」一列写「已核实」，或者「推翻，因为……」。
- 「改法」之前先判**在哪一边**：每个组件有它处理的事和它不该知道、不该决定、不该等的事。是该处理的地方没处理，还是不该处理的地方处理了？后者是泄漏，改法写成「X 归谁处理」，不写「给 Y 加 X」。
- 「触发条件」写具体的输入、配置或时序；「多常见」写常见、少见或几乎不会；纯结构和措辞类的发现（没有运行时后果）这两列写「—」。
- 「级别」一列写「挡合并」或「Nit」，按概率乘以后果定。表按这个顺序排。
- 表后用一段话说明：哪几条其实是同一个根因，先改哪条最划算，以及哪些地方已经写得好、不要动。最后一项照 Google 审查指南的要求：看到好的地方，也要说出来。
