# agent-brief

## 为什么是这个形状

依据 arc 做过的一次对照实验(第 6 轮,同一道题、不同的 brief 写法):

- 七段通用因子全给(G9)综合最好:概念 137(只给题 445)、最大模块环 1.3、公开函数 21.7。
- 单个因子里 FP/Haskell 最强;信息隐藏单独给最差(把状态藏成可变对象);人类提示("注意 X")让设计变小但命名最差、不稳。
- 方法结论:最有效的不是告诉 agent 要注意什么，而是换掉它思考的形状 —— 先用 ADT 和纯转移写出模型，再翻译成 Rust。

局限: 每组 3 次、机械信号、只看倾向;"G9 + 人类提示"没跑过;实验是隔离运行(不读全局 CLAUDE.md)。

## 组装顺序(和实验一致，问题永远最后)

1. **北极星** —— 这次任务是什么，一两句。由派活方写，不夹带解法。
2. `components/principles.md` —— 原样
3. `components/fp-haskell.md` —— 原样
4. `components/thinking-altitude.md` —— 原样
5. `components/thinking-information-hiding.md` —— 原样
6. `components/formal-hint.md` —— 原样
7. `components/rubric.md` —— 原样
8. **裁定** —— 维护者已定的事和不许碰的边界，用原话，标日期。只写事实和决定，不写"注意 / 小心 / 记得"。
9. **相关对话** —— 这次任务牵涉的那几段对话原文 (用户原话、审查原文、被纠正的提议和纠正的话), 带日期和说话人, 不转述; 贴不下的给查询途径 (会话记录 `~/.claude/projects/<project>/<session>.jsonl` 的路径, 让它 grep) 并点明查什么。监督会话自己的推断另起一小节, 标「推断, 可以反驳」; 和原文或 repo 定论冲突时 agent 先停下报告。裁定先写进 repo 文件或 issue (堆), brief 指向那一行; 只在会话或 scratchpad 里的 (栈) 不算定论。依据: 子 agent 分不出转述和原话, 照转述里错的做 (arc 维护者 2026-11-01:「你直接贴对话过去它都不会错」「重要信息要在 heap 不是 stack 里面」)。
10. **问题** —— 要做什么、在哪做(worktree / 分支)、验收清单(题目要求的功能逐项列出，G9 设计小，会漏没被要求的)、交回什么。

第 2–7 段原样拷进 brief(`cat` 拼接)，不改写、不摘要。

## 先交模型再写代码 (只在代码还没成型时)

arc 维护者 2026-11-05:「你就一个bug fix为什么要改模型？」「规矩修改一下。模型如果代码成型了可以丢掉」(2026-11-01 也说过:「改屁模型啊」「模型是让你开始思考的」)。

- **代码还没成型** (新设计、新包、从零写): 照下面要模型。
- **代码已经成型** (bug fix、审查发现、普查清单、搬家改名、在现有结构上改): brief 不要模型, 第 3、4、6 段里要 `model.hs` / `model.md` / `spec.md` 的句子不拷进去 (只给第 2、7 段, 或在问题里写「不写模型文件」); agent 按归属想清楚, 判断写在交回里。已有的模型文件删掉, 不同步。

第 3、4、6 段要求 agent 在动手前写出 `model.hs`(数据类型 + 签名)、`model.md`(状态机、每个值的路径、每个模块"知道什么 / 不知道什么"两栏)、`spec.md`(状态、事件、转移、不变量)。brief 的"问题"里写明这三份放在哪(agent 的 scratchpad 或 PR),以及交回时附上。写完核对: Rust 里每个类型和函数在 `model.hs` 里都有原型;多出来的要么模型漏了，要么不该存在。

## 一次改好，不打补丁

arc 维护者 2026-10-24:「让他们一次改好，不要总补丁，事实上，补丁出烂活」。那天的 presubmit agent 交回后被追加了约 8 条消息、四五十个改动点，每条一改一编译，跑了近一小时，代码长到 630 行，还冒出 `Ending` / `CheckFailure` / `OnPass` 这类为补丁而生的概念。

**派活方(监督会话)**:
- 派之前把这次要的东西收齐: 裁定、审查发现、验收清单一次写进 brief。审查结果没出来就先等，不要一边审一边往运行中的 agent 里塞。
- agent 跑着的时候冒出新的裁定或发现，不要逐条 SendMessage 追加。小于一条且不改形状的可以带一句;会改形状的(删 / 合并类型、换位置、改边界)就停掉它，把新旧要求合成一份新 brief 重新派。
- 一个 agent 只收一份 brief,交回后最多一轮合并后的修改说明。

**写进 brief 给 agent 的一句(放在"问题"里)**: 新信息先改模型(`model.hs` / `model.md` / `spec.md`),再按模型重写受影响的代码;不在旧代码上逐条打补丁，交回前核对每个类型和函数在模型里都有原型，没有的删掉。

## 修 bug / 改审查发现

审查发现就是"问题"那一段的内容，照样列(带 file:line 和证据)。但要求 agent 先在模型里找到这条发现对应的那一行，改模型，再改代码 —— 不对着清单逐条打补丁。

## 收尾(仓库约定照旧)

worktree、`arc submit`、不轮询合并结果、新定义清单、本地按 diff 选检查 —— 这些是仓库 CLAUDE.md 的事实，写进"问题"的交回部分，不另起一段提示。
