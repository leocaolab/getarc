# 7 层检查

一段代码"做完", 是它在七个互相独立的角度上都站得住。每层一个只看这一层的审查者: 同一个人同时看命名和错误处理, 两边都看不深。

## 七层

规则原文随插件附带, 在 `${CLAUDE_PLUGIN_ROOT}/rubrics/` 下; 每条规则一问一答, 带理由和正反例。审查时让 agent 读原文, 不读这里的摘要。

| 层 | 看什么 | 用的 skill | 规则原文 (`rubrics/`) |
|---|---|---|---|
| **name** | 类型名是名词、不用填充词、不造词、不撞名; 每个类型和文件名都过, 包括已有的; 文件名也是名字, 看每个文件是不是一件事。撞名 grep 不算名字检查 | `name-check`、`type-naming` | `type_design.yaml` 第一组 |
| **type** | 每条类型规则; 形状三条 (total: 非法值造不出来; 规范化: 一个事实一种表示; 透明度和不变量匹配) | `name-check` 的「形状」一列 | `type_design.yaml` 全部 |
| **taste** | 安全 / 正确 / 设计 / 品位, 四路各自独立看 | `taste-check` | 各路引的原文 |
| **hex** | 权重最高, 结论放最前。FP 纪律: `Option` / `Result` 不在半路拆开, 在里面用 `map` / `and_then` / `?` 组合; 核心逻辑是纯 `a -> b`, 纯判断返回事实, 不返回 `Result`; 失败和副作用留在外层; 只在有资格决定两条路的那一层 (边缘 / main / 调用方) 拆一次, 两条路都处理。逐个签名查: 返回 `Result` 或做副作用的"纯"层、半路拆 (`unwrap_or` / `.ok()` / 默认值 / 丢掉一条路的 `match`)、在没资格决定的层拆。判断与机制分开: 判断的签名里没有容器、没有 `&mut`; 存、搬、攒、排、计时的东西 (IO、缓冲、队列、时钟) 是机制, 由机制调用判断。每个组件写清它处理什么、**不**处理什么; 一个事实或决定越过了边界就是泄漏, 修法是把它送回该在的地方, 不是在越界处补 | — | `fp_lens.yaml`、`l5_architecture.yaml`、`effect_state.yaml` |
| **error** | 每处会失败、吞错、panic 的地方: 现实里会不会发生、失败域、谁有能力决定、人怎么知道 | `error-check` | `l4_contracts.yaml`、`rust_best_practices.yaml` |
| **破坏者** | 写能编译、真跑起来的测试去打它; 只有真跑出来的才算 | `test-check` | — |
| **comment** | 逐条 grep 看, 不凭印象: 为假的、复述代码或签名的、讲历史的、计划代号和看板编号当理由的、第一句不是动词开头的 | `coding-convention` 的「注释」节、`comment-clean` | `comment_hygiene.yaml`; 项目自己的编码规范 |

层不换: 不拿别的检查顶替其中一层, 也不漏 comment。写修复代码前另加载对应语言的 `shift-left-*`。

## 输出的形状

每层先从第一性推出这个东西在这一层应当是什么样, 再对照现状和真实的替代方案 (再找第三条路), 各自 pro/con, 给结论; 不是一张"问题清单"。「现状就是这样」「设计文档这么写」不是理由, 设计文档本身也在审查范围内。发现 = 现状无充分理由地偏离推出的形状的地方。每条:

- `file:line` + 证据 (代码原文或测试输出), 自己在树上核过; 核实不了的不写, 或标「推演」;
- 本质: 什么结构问题的症状;
- 什么条件下出问题、多常见;
- 建议形状与改法, 严重度 (阻断 / 应改 / 可选); 纯风格标 `Nit:`。

"看着像问题但其实对"的也列一行, 说为什么。

## 怎么跑

1. **定范围、分组。** 小的模块一个 agent 跑全部 7 层; 大的每层一个 agent, taste 再分四路。全仓时按模块分组, 每组一个 agent 或一组 agent。
2. **写共用的说明, 写进文件。** 目标、负责人的原话 (带日期, 贴原文不转述)、本 skill 的路径、范围 (只读的那棵树、提交号、不审的部分)、交回路径。会话上下文会被压缩, 所以说明和裁定写进仓库里的文件, agent 去读那个文件。每层的规则让 agent 去读 `rubrics/` 原文, 说明里不摘要。
3. **派活: 只审不改。** 审的 agent 只读一棵干净的检出 (例如 `origin/main` 的 worktree); 破坏者在自己的临时 worktree 里写测试, 交回后删掉, 测试代码贴进报告。不开 PR、不提交。
4. **报告进仓库。** 例如 `docs/review/<日期>-7layer/<组>.md`, 节内按 hex、name、type、taste、error、破坏者、comment 排; 末尾汇总表 (模块 × 层 → 阻断 / 应改条数) 和"跨模块的同一种病"。
5. **主会话核实、裁定。** 每条拿代码核过; 层与层冲突时按负责人的原话裁, 裁定写进那一轮的 `README.md`, 带原话。要负责人定的, 列成带选项的问题。
6. **记成待办、分批修。** 第一轮: 阻断、安全、存活, 每批一个 agent、一个 PR; 第二轮: 其余的应改 (name / type / comment / 品位), 按模块分批。
7. **独立复审当门, 自查不是。** 每批交回后, 另派一个只拿 diff 和规则原文、不拿主会话结论的 agent 过 7 层。子 agent 的自查表不算证据: 它看到的是主会话的转述, 转述错了它也照着错。

## 能机器判的部分做成检查

7 层里能机器判的, 做成每个 PR 都跑的检查, 不等下一轮人审:

- **hex / 分层**: 依赖方向检查 —— 哪个包能依赖哪个, 违例清单只许变少。用 arc 的话是 `arc archcheck --base <base>` (规则在仓库的 `.arc/archcheck.toml`)。
- **name**: 新加类型的名字 —— `name-check` 的脚本列出新类型, 用了填充词、不以名词结尾、撞名的先筛出来当候选; 判过的记下来, 不重复判。
