# 先建模, 再写代码

规则清单挡不住坏代码: 先按习惯写出来, 再回头一条条打勾, 改的是措辞不是结构 (改个名字过了名字检查的胶水类型照样是胶水; 加告警"满足"了"两份不许不一致")。所以写的时候不对照清单, 而是**先把这个东西在现实里是什么写下来, 代码是它的翻译**。清单留给查的一方 (本文末节)。

## 四步 (第 1 步写四张表)

**1. 写归属, 在写任何代码之前 —— 正面、反面、边界三张。**

表是记答案的地方, 不是答案: 把格子填满不等于想过 (表填得整整齐齐、照样把连接的路由号写进了记录的, 实验里有)。每个事实先问三句, 主人从答案里出来, 不是从"哪个结构体里正好有这个字段"出来:
- **它因何而生、活多久?** 世界里哪个动作产生了它; 那个动作结束之后它还有没有意义。一个连接的路由号, 连接一断就没有了, 它不进半年后才有人读的记录。
- **它的不变量谁能独自担保?** 只看得见自己的一方担保不了全局的不变量: "一个 runtime 同时只归一个会话", 会话看不见别的会话, 只有编号表看得见全景。能担保的那一方是主人, 别的一方不持有它。
- **谁能不借别人的证据就宣布它?** 要先问别人才知道的, 不是它的源头: 预热器要问内核才知道进程死了, 死就只由内核报。

三句之外还有一条: **物理上看不见、管不着的事, 不发明机制去补。** 上游的约定有洞, 停在边界报上去。

正面, 每一方**能做什么**: 它拥有哪些事实 (谁产出、在哪一刻), 它决定什么。

| 事实 | 谁产出、在哪一刻 | 主人 | 谁据它做决定、决定什么 |
|---|---|---|---|

反面, 每一方**不做什么** (负能力): 它不知道什么、不决定什么、不等什么。反面和正面一样要写全 —— 越界的修法往往就是让一方开始知道它本不该知道的东西, 只有写下来才看得见。

边界, 每两方之间**越过什么**: 哪些事实、以什么形式 (一个事件、一个数字、一个决定) 从一方交到另一方; 除此之外的东西不越过。

三张写不出来, 就是还没想清楚, 先别写代码。

**然后退一步, 写流转 —— 第四张。** 每个事实一行, 从它产出的那一刻走到它最后落下的地方 (产出 → 判断 → 暂存 → 记录 / 回答), 每一格写: 此刻哪个状态机的哪个阶段拿着它、拿着的是哪个类型。

| 事实 | 产出 | 经过的阶段 (谁拿着、什么状态) | 落下 | 类型 |
|---|---|---|---|---|

- **一行只有一个类型。** 事实穿过阶段时不改名、不换形状; 变的是拿着它的容器和状态。一行里出现第二个类型 (换了阶段就换了名字: `CallFact` → `UnownedFact` → `RuntimeFacts`), 就是在给阶段造名词。
- **一个事实只有一行、一个产出者。** 两行说的是同一件事 (内核报的死、预热器又报一次死), 砍掉多出来的那个来源。
- **阶段是状态机的状态, 不是新概念。** 一个状态里只放推进这个状态要的东西; 终态之后它就不在了 (类型上没有一个结束了还能推进的值)。
- **决定带着它的证据流下去。** 判断产出的决定装着执行它要的全部事实, 下游不回头再查输入、不补一个"不可能"分支的值。

改代码 (修一个发现) 时同样先找到这张表里那一行: 这个事实已经是哪个类型、在哪几个阶段之间走。修法可以给它加一个阶段、换一个持有者; 不可以给它再造一个类型。现成的接口逼你去造别人的值 (替别人编一句原话、为凑参数造一个"结论"类型) 时, 改的是接口, 不是去造。

四张表是整个方法里唯一需要动脑的地方, 后面三步都是翻译。

**2. 类型从表里翻译出来。** 每个主人一个类型, 它拥有的那几行是它的字段或变体; 一个事实只出现在它的主人那里。表里没有的类型不出现 —— 于是"为了在两个函数之间带东西"的胶水、"为了补依赖缺的接口"的塞子没有地方长出来。名字就是那一行里那个事物的名字, 不另起。只在某个状态才成立的事实, 放进那个状态的变体里。翻译完每个类型过形状三条 (说的是数据类型, 不是函数):
- **total**: 这个类型能装的每一个值都是合法状态; 不合法的组合在类型上造不出来, 而不是"这种组合不会发生"。
- **normal**: 每个合法状态只有一种表示; 同一个事实不存两份, 能算出来的不另存, 不用 0 表示"关"又另有一个 `Off`。
- **transparent**: 不透明程度和不变量匹配; 有不变量的字段私有、只经 `parse` / `new` (返回 `Result`) 构造, 没有不变量的字段公开、不搞 getter 仪式。

类型的反面, 一个类型**不装**:
- 别人的事实 —— 只装它的主人拥有的那几行;
- 机制 —— 句柄、缓冲、连接、IO 错误、时钟属于边上, 不进领域类型;
- "没读到" —— 那是 `Result` 的 `Err`, 不是这个东西的一种状态;
- 为了凑参数放在一起的东西 —— 那不是一个事物。

**3. 判断从表里翻译出来。** "谁据它做决定"那一栏的每一项, 写成一个纯函数: 输入是它用到的那几个事实 (标量、定长数组、切片), 输出是决定。存、搬、攒、排、计时的东西 (IO、缓冲、容器、队列、时钟) 是机制, 写在边上调用判断, 自己不判断。

**4. 注释从表里翻译出来。** 代码说不出的只有两类: 为什么这样 (表里那个事实的来由、外部约束) 和不知道什么 (反面那一行)。照着表写这两类, 别的不写; 格式照末节「注释」。

写完拿四张表回头对一遍: 流转表每一行在代码里是不是只有一个类型? 新造的每个类型, 是表里哪个事实、哪个阶段的容器? 每个类型对得上正面的一行吗? 有没有哪个类型知道了反面那一行说它不知道的东西? 两方之间传的, 是不是只有边界那张表里列的? 对不上的那一处, 不是代码写错了, 就是表漏了 —— 先补表, 再改代码。

## 例子: 预热池 (一个提前启动 runtime 的模块)

**1. 归属** (正面)

| 事实 | 谁产出、在哪一刻 | 主人 | 谁据它做决定、决定什么 |
|---|---|---|---|
| 要备几个热的、最多同时起几个 | 部署配置, 启动时 | 预热池的规则 | 预热池: 这次起几个 |
| 哪些 runtime 在启动、哪些已就绪 | 编号表, 编号与转手时 | 编号表 | 预热池只读个数 |
| 有几个会话在等 runtime | 会话表, 会话开始等时 | 引擎 | 预热池只读个数 |
| 一次启动的结局 (起好 / 起失败 / 没就绪就死) | 适配器或内核, 结局到达时 | 预热池的健康 | 预热池: 退避多久、告不告警、停不停 |

反面: 预热池不知道哪个会话要 runtime、为什么要; 不持有任何一个 runtime (在哪是编号表的事); 不知道调用。会话也不知道它拿到的 runtime 是不是预热好的。

边界: 编号表 → 预热池, 只有个数 (启动中几个、就绪几个); 引擎 → 预热池, 只有在等的会话数和"一次启动的结局"这个事件; 预热池 → 引擎, 只有一个决定 ("再起 n 个") 和告警。没有一个 runtime 编号、没有一个会话名越过这条边界。

**2. 类型** —— 每行落在它的主人那里:
- "一次启动的结局"累积成预热池的健康: `PoolHealth { Healthy, Failing { streak, last, retry_at }, Stopped { last } }`。`retry_at` 只在 `Failing` 里, 因为只有在退避时它才是一个事实 (放在外面, 池子停了它还留着旧值, `next_deadline` 就永远指向过去 —— 这正是没有先写表时出过的 bug)。
- "哪些在启动、哪些就绪"在编号表里, 预热池只拿到个数 `Stock { ready, starting, waiting }`; 预热池里没有 runtime 的列表 (有了就是第二份, 两份要对账)。

**3. 判断** —— 每个"决定什么"一个纯函数:
- 这次起几个: `fn start_count(target, max_starting, stock) -> usize`。
- 再失败一次之后的状态和要不要告警: `fn after_failure(streak, alert_after, first_backoff, max_backoff) -> (Streak, bool)`。
- 机制 (发出启动命令、读钟) 在引擎和适配器里, 拿着这两个函数的结果去做。

**4. 注释** —— 只写负能力那一行:

```rust
//! Starts runtimes ahead of need. It is told how many are starting or ready and does not keep
//! them: where each runtime is belongs to the runtime table. It does not know sessions, and a
//! session does not know whether its runtime came warm.
```

没有先写表时, 同一个模块的说明是这样的 —— 内部代号、复述代码做什么、一句话塞了几层:

```rust
//! S3, the warm pool: runtimes started ahead of any session (§13.3 S3). It decides how many to
//! start and when — after a failure it backs off, at a permanent one it stops — and says when
//! starting fails or recovers. …
```

## 查的时候对照

写的时候走上面四步; 查一段已经写好的代码 (自己的或别人的) 时, 逐条对照下面这些。

### 注释

**默认不写。** 读代码就能看懂的地方, 不写注释。

> 注释通常应该解释代码为什么存在, 而不是解释代码在做什么。如果代码不够清楚、自己说明不了自己, 就应该把代码改简单。—— Google《审查看什么》

写之前先过三问:
1. **能不能改代码, 让这条注释没必要写?** 改个名字、拆出一个函数、把逻辑写简单。能, 就改代码。
2. **它是不是在复述代码或签名?** 是, 就删掉。
3. **它是不是说了代码说不出来的事?** 只有这几种可以留: 为什么这么做 (外部约束、绕过的 bug、顺序或并发上的要求、为什么不走显而易见的那条路); 调用方看不见的东西 (副作用、什么时候出错或 panic、单位、边界情况); 类型表达不出来的不变量 ("永远不为空: 只有 `new` 能造"); 负能力 (不是一眼能看出时)。

基本格式:
- **代码里的注释和文档用同一种语言** (推荐英文), 测试、证明、迁移 SQL 也一样; 同一个概念在一个文件用一种语言讲、在旁边用另一种再讲, 跨文件的拷贝就 grep 不出来。设计文档 (`model.md` 等) 不在此列。
- **每条注释都是一句完整的话**, 有主语有谓语, 不说半截话。
  - ❌ `/// Which CPUs this process may use, and pinning threads to them.`
  - ✅ `//! Finds the CPUs this process may use and pins threads to them.`
  - ❌ `/// On macOS, performance cores only.`
  - ✅ `/// Returns how many physical cores can be busy at once; on macOS only performance cores count.`
- **函数文档第一句用第三人称动词开头**: `Returns …`、`Waits until …` (RFC 1574; Google C++ 风格指南写 `Opens the file`, 不写 `Open the file`)。Python 的 docstring 按 PEP 257 用祈使句: `Return …`。类型的文档同样用第三人称动词开头 (`Holds …`、`Numbers …`、`Counts …`), 不用名词短语 (与 `comment_hygiene.yaml` 的审查规则一致); 字段的文档也要成句。
- **字段或枚举变体**, 只在补充了单位、取值范围或不变量时才写。
- **最多一两句人话**, 让新来的人看得懂。不写改动历史 (git 里有; 包括"已删掉的 X""某天谁裁定的""第二轮发现的"), 不逐步讲解实现, 不用外人查不到的内部黑话 (状态机代号如 "S3"、小节号或看板编号代替理由)。issue 编号只是个指针, 不能当理由。
- 会出错的公开函数写 `# Errors`, 会 panic 的写 `# Panics`, `unsafe fn` 写 `# Safety`; 每个 `unsafe` 块前写 `// SAFETY:`。
- 检验: 把代码遮住只看注释, 应该能看出设计者的意图和埋着的雷, 而不是一步步的操作。

三条评分规则:
1. **写背景, 不翻译逻辑。** ❌ `// 检查列表是否为空, 如果是则返回错误。` ✅ `// 先在这里拦下空列表: 放过去的话, 下游网关会回 502。`
2. **暴露边界和副作用。** ❌ `/// 解析传入的 payload。` ✅ `/// 只认 &str 和 String 两种 payload, 别的换成一句固定文字, 不会 panic。`
3. **动词开头, 一句说中。** ❌ `/// 这个函数的作用是负责把线程挂起, 直到超时。` ✅ `/// 等线程结束; 到了 deadline 还没结束就放弃它, 免得关机卡死。`

一个读 CPU 拓扑的模块的例子:

```rust
// 删掉: 复述签名
/// The lowest-numbered CPU of the core.
pub fn first(&self) -> CoreId

// 留下: 代码里看不出为什么
/// Counts cores within the affinity mask, not across sysfs: sysfs lists every host CPU, so a
/// container on 32 of 64 cores got 64 threads, half of them on the other half's SMT siblings.

// 留下: 调用方看不见的副作用
/// Threads started afterwards inherit the mask, and so do processes they fork.

// 留下: 类型表达不出来的不变量
/// The allowed CPUs of one physical core. It is never empty, because only `new` makes one.
```

### 类型

- **一句外行听得懂的话说出它是哪个真实事物。** 结构是现实里的一个实体; enum 是几种状态之一, 或者几种失败之一, 拿来 `match`。说不出来, 它多半在补管道上的洞 (协议缺标签、分层挡路、布局需要、推迟了一步): 找到原因消掉它, 不给它换好名字。没有领域的东西很虚, 一查一个准。
- **它是哪个事实? 这个事实是不是已经有类型了?** 把新类型和代码里说同一件事的类型放在一起比 (有界文本有两份、死有两个来源); 一个事实在不同阶段换了名字, 合回一个。为凑参数、为过参数个数上限而造的"结论""上下文"类型, 不是一个事物。
- **它可以删除吗?** 补依赖缺口的包装、一个生产实现的 trait 的测试实现、测试里抄一遍生产的组装步骤, 都是塞子。
- **形状三条**:
  - **total**: 每个值都是合法状态; 只在某个状态才有的字段放进那个变体, 总是一起出现的两个 `Option` 合成一个。
  - **normal**: 每个状态一种表示; 一个事实不存两份, 一个关系不在两处各记一份。
  - **transparent**: 有不变量的字段私有、只经 `parse` / `new` 构造; 没有的字段公开。
- **为事实建模, 不为今天的调用方建模**: 读不到是 `Result` 的 `Err`, 不是这个东西的一个变体。
- **错误按失败的种类**: 几种 → 枚举, 每个变体带类型化的事实; 一种 → 字段全类型化的结构体; 种类不写进 `String`, 底层错误不抹成 `Box<dyn Error>`。
- 逐个过 `${CLAUDE_PLUGIN_ROOT}/rubrics/type_design.yaml` (判据原文)。名字检查过了不等于过关: 改了名的胶水照样是胶水。

### 命名

两条判据:
1. **大家怎么叫就怎么叫。** 先查标准库和语言指南 (Rust std 与 [API Guidelines](https://rust-lang.github.io/api-guidelines/naming.html)、Python 的 PEP, 子解释器就是 PEP 734 的 `Interpreter`)、内核与行业 (Linux、PostgreSQL、Ray / Flink 的 worker 和 slot) 里同一个东西的名字, 有就用它。审稿人已经给出通称的, 用通称, 不用自己的。
2. **只有找不到通称时才造词, 造出来的词含义必须明确**: 只看名字就知道它装的是什么。`lane` (一个仓库里能有四种意思)、`Answer`、`Said` 是含义不明确的典型。

- **类型名是名词**, 以名词结尾 (`AbandonedThread`, 不是 `Abandoned`); 状态枚举用名词, 变体可以是形容词。不用光秃的动词或过去时 (`Reject`、`Said`), 不用填充词 (`Manager`、`Helper`、`Data`、`Info`、`*Context`、`*Parts`), 不用取自用法的修饰词 (`CapturedX`: 先只看名字猜意思, 再读定义)。错误类型照 std 叫 `<动词><宾语>Error` (`ParseIntError`, 不是 `NotAHello`), 变体说死因 (`NotFound`、`NotDelivered`)。
- **用行业里的那个词, 不用日常比喻**: 先问这件事在操作系统、网络、分布式系统里叫什么, 用那个词 (`Isolation` 不是 `Place`, `Reply` 不是 `Answer`, `RuntimeExit` 不是 `Death`, `run_until_idle` 不是 `settle`, 测试装置是 `Harness` 不是 `World`)。日常词对写的人顺口, 读的人要先猜比喻再翻回来。名字放进一行调用里念一遍, 叠词 (`end.end`) 和读不通的组合 (`Answer::Ended`) 同样要改。判据原文: `type_design.yaml` 的 `metaphor-word-in-place-of-the-fields-term`。
- **测试按它测的形状命名**, 不按来历 (`regression_*`、`breaker_*`、机器名)。
- 大小写与转换按语言惯例 (Rust: [C-CASE](https://rust-lang.github.io/api-guidelines/naming.html#c-case)、[C-CONV](https://rust-lang.github.io/api-guidelines/naming.html#c-conv); getter 不加 `get_`); 缩写当一个词 (`Uuid`)。
- **名字难起, 是设计出了问题** —— 回到第 1 步。

### 品位

- **判断与机制分开**: 每个判断是一个函数, 输入是它据以判断的事实 (标量、定长数组、切片), 输出是决定; 存、搬、攒、排、计时的东西 (IO、缓冲、容器、队列、分配、时钟) 是机制, 机制调用判断, 判断不碰机制。检验: 判断的签名里没有容器、没有 `&mut`, 它的边界测试只用标量。**只转发参数的中间层删掉。trait 只在有两个真实实现、或测试必须换掉副作用时才加。能返回决定, 就别在判断里做事。**
- **生成式测试 (proptest、排列、批大小穷举) 只打纯判断**: 每个用例毫秒级、不起进程、不开库、不写文件; 性质说的是判断 (幂等、到达先后无关、等于预言模型折叠), 就让判断吃事实做参数来测。真 git / 真库 / 真 `sh` 只留一两条手写的端到端用例证明接线。生成式测试要先 push 进仓库、开库才测得到, 说明判断还埋在机制里, 先拆判断, 不给机制加重放 trait、模板库、并行来提速 (一个真实的例子: 256 个生成的脚本, 每个起 30 多个 git 进程, 一共两万五千个进程跑了 8 分钟; 另一个把 120 种排列各开一次数据库、各跑一遍全部迁移)。
- **每一行都有代价**: 删掉一行行为不变, 它就不该存在。**特殊情况在数据结构里消掉**, 不在每个函数里补。**同一个事实只存一份。接口要窄, 实现可以深**: 没有外部调用方的不 `pub`。
- **能在语义上让错误不存在, 就别让它成为错误**, 但真实的失败带着原因返回。**只解决现在知道要解决的问题。改签名之前先看调用方。**

### 错误处理

每个 `Option` / `Result` 先问真实世界里会不会发生: 会, 带着原始输入和真实错误传给能决定的那一层; 不会但编译器不知道, 改类型让它写不出来; 类型改不了才 `expect("<证明>")`。不顺手 `unwrap`, 也不吞 (`unwrap_or(默认)` / `.ok()` / `let _ =`), 也不机械地 `?` (主循环里一个 `?` 会把一条小失败放大成停机)。规则原文在 `${CLAUDE_PLUGIN_ROOT}/rubrics/l4_contracts.yaml` 与 `rust_best_practices.yaml`。

依据: Google [C++ 风格指南](https://google.github.io/styleguide/cppguide.html#Comments)与 [Python 风格指南](https://google.github.io/styleguide/pyguide.html#38-comments-and-docstrings)的注释一节、Google 审查指南[《审查看什么》](https://google.github.io/eng-practices/review/reviewer/looking-for.html)、Rust [RFC 1574](https://rust-lang.github.io/rfcs/1574-more-api-documentation-conventions.html) 与 [API Guidelines](https://rust-lang.github.io/api-guidelines/)。
